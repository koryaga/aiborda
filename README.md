# dom-agent

Веб-приложение, в котором LLM живёт внутри страницы. Пользователь правит DOM
руками — в полях ввода и через инструменты разработчика браузера — и нажимает
«отправить». Модель получает диф правок, отвечает JavaScript-кодом, код
исполняется и меняет тот же DOM. Страница одновременно интерфейс, состояние и
память агента.

Два инварианта:

1. Код модели всемогущ внутри образа и бессилен снаружи.
2. Состояние страницы не попадает в контекст извне. От пользователя приходит
   только диф; состояние модель читает сама, вернув нужное из кода.

Спецификация — [docs/superpowers/specs/2026-08-19-dom-agent-design.md](docs/superpowers/specs/2026-08-19-dom-agent-design.md).

## Запуск

Нужен Node ≥ 20 и файл `~/.pi/agent/models.json` от инструмента `pi`.

```bash
npm install
npm start
```

Открыть `http://127.0.0.1:8730`. Путь к конфигу переопределяется флагом
`--pi-config` или переменной `PI_MODELS_PATH`. Конфиг перечитывается по
`SIGHUP` и по `POST /api/reload`.

```bash
npm test
```

Список моделей берётся из `enabledModels` в `~/.pi/agent/settings.json` — того
же файла, которым вы отбираете модели в самом pi. Работают и пользовательские
провайдеры из `models.json`, и встроенные в pi, включая openrouter: у
встроенного провайдера есть собственный поток, поэтому `openai-responses`,
`google-generative-ai` и `openai-codex-responses` не потребовали адаптеров.
Модель по умолчанию берётся из `defaultProvider` и `defaultModel`.

Если `enabledModels` пуст или файла нет — прежнее поведение: всё из
`models.json` плюс найденное discovery. Встроенные провайдеры в этом режиме не
подключаются: без отобранного списка они дали бы около четырёхсот пунктов в
селекторе.

Учётки oauth читаются, но **никогда не обновляются**: dom-agent не пишет в
`~/.pi/` ни при каких условиях. Обновление выдало бы новый refresh-токен и
погасило старый, сломав вход у самого pi. Истёкший вход виден в заметках под
панелью вместе с советом войти заново.

Сервер слушает только петлю и проверяет заголовок `Host`: одного `bind` к
`127.0.0.1` мало, потому что домен атакующего, резолвящийся в `127.0.0.1`,
даёт его странице читать ответы как свои.

## Решение по `@earendil-works/pi-ai`

Шаг 0 исходного плана — выяснить, читает ли пакет `models.json` сам.
Проверено по типам установленного `pi-ai@0.84.2`:

**Свой загрузчик файла нужен, свои адаптеры провайдеров — нет.**

Наружу пакет отдаёт только `InMemoryModelsStore` и `InMemoryCredentialStore`;
чтение `~/.pi/agent/*.json` с диска живёт в `dist/cli.js` и не экспортируется.
Поэтому `server/pi-config.js` разбирает файл сам.

Зато адаптеры готовы и берутся как есть:

```js
import { stream } from '@earendil-works/pi-ai/api/openai-completions';
```

Сигнатура `(model, context, options) => AssistantMessageEventStream`,
`apiKey` и `signal` принимаются прямо в вызове. Регистрировать провайдера и
заводить credential store не нужно, `server/providers.js` не написан.

Побочное следствие, снявшее целый пункт спецификации: рассуждения приходят
**отдельным типом события** (`thinking_delta` против `text_delta`), поэтому
«срезание thinking» сводится к тому, чтобы читать только текстовый канал.
Регулярка в `server/parse.js` осталась второй линией обороны — для
провайдеров, вкладывающих `<think>` прямо в текст.

## Что сделано в вехе 1

Шаги 1–4 плана: конфиг с discovery, HTTP-сайдкар, образ с исполнением кода,
захват правок человека, разбор ответа модели, ход со стримом, оболочка.

Не сделано, ждёт вехи 2: карта образа после сброса, триггеры сброса истории,
счётчик токенов в UI, очередь и пауза, watchdog с восстановлением, журнал и
снапшоты на диск.

## Наблюдения первого прогона

Сквозной цикл работает: `gemma4:12b-mlx-64k` через локальный ollama получает
диф, отвечает кодом, код исполняется в образе и меняет разметку. Ход занимает
десятки секунд — это генерация 12B-модели, а не накладные расходы.

На холодном старте модель ответила чистым JavaScript с первой попытки: без
обёрток из обратных кавычек, без вводных фраз, автоповтор не понадобился. И
сама воспользовалась `#notes` для заметки себе — контракт из системного
промпта дошёл.

**Замеченное неудобство для вехи 2.** Модель объявлена `reasoning: true`, и
рассуждения приходят каналом `thinking_delta`, который мы намеренно не
показываем. Пока она думает, оболочка молчит десятки секунд: индикатор стоит
на «думает», в логе пусто. Формально верно, на практике похоже на зависание.
Стоит показывать хотя бы факт того, что рассуждения идут.

**Ещё одно, тоже для вехи 2.** Диф теряется безвозвратно, если запрос к
сайдкару не дошёл: образ очищает буферы в момент сборки дифа, до того как
станет известно, доедет ли он. Правки человека при сетевом сбое пропадают.

Систематического замера доли ходов, где код исполнился с первой попытки, ещё
нет — это шаг 7 плана и он относится к вехе 2. От этой цифры зависит вопрос о
grammar-режиме; `pi-ai` его поддерживает (`openai_lark`, `openai_regex`), так
что запасной путь есть.

Проверено на живом образе (веха 1, образ ещё был `iframe sandbox="allow-scripts"`
со склеенным `srcdoc`): `localStorage` и `document.cookie` бросают
`SecurityError`, `parent.document` недоступен, любой `fetch` умирает на CORS —
включая запрос к тому же серверу, который отдал оболочку. `origin` образа —
`null`, поэтому `event.origin` как проверка отправителя бесполезен: работает
только сверка `event.source` и совпадение `id` с ожидающим запросом.
Незапрошенное сообщение от образа оболочка отбрасывает — код модели способен
вызвать `parent.postMessage` и иначе подсунул бы в контекст произвольный текст
под видом правки человека.

**Задачей 3 это заменено**: образ переехал на свой origin (второй HTTP-порт,
без `sandbox`), поэтому `localStorage` и остальной HTML5 теперь работают,
а `event.origin` — настоящий адрес образа, а не `null` (проверка `e.source`
и совпадения `id` осталась как есть, `event.origin` сверяется рядом с ней).
`parent.document` и `fetch` к оболочке по-прежнему недоступны — тем же
изолирующим механизмом Same-Origin Policy, только теперь через различие
портов, а не через `sandbox`. Подробности — в «Устройство» ниже.

## Устройство

```
server/
  index.js       два HTTP-сервера (оболочка и образ), статика, /api/*
  pi-config.js   разбор models.json и auth.json, встроенные провайдеры, периметр наружу
  pi-settings.js разбор settings.json: отобранный список моделей и умолчание
  parse.js       ответ модели → исполнимый код
  context.js     системный промпт, история сообщений
web/
  index.html     оболочка
  shell.js       ход, разбор потока, обмен с образом
  image-boot.js  наблюдатель, атрибуция, диф, снапшот, исполнение
  image.html     заготовка образа, подключает image-boot.js тегом script
  style.css
```

Образ отдаётся вторым HTTP-сервером на отдельном порту (по умолчанию 8731) —
это и есть весь механизм изоляции: другой origin даёт `<iframe>` без
`sandbox` полноценные `localStorage`/`sessionStorage`/`indexedDB`/`cookie`,
но не даёт достать до DOM оболочки. Оболочка узнаёт адрес образа через
`GET /api/config` и сверяет его с `event.origin` входящих `postMessage`.

`web/image-boot.js` не имеет импортов и объявляет одну функцию: подключается
на образе обычным `<script src>`, сборщика в проекте нет. Тесты берут тот же
текст и выполняют его в jsdom, поэтому проверяется ровно то, что исполняется
в браузере.

## Две вещи, о которые стоит не споткнуться

**`node --test test/` не работает на Node 26.5.0** — раннер пытается
разрешить директорию как модуль. В `package.json` стоит `node --test` без
пути; автопоиск находит те же файлы.

**Пути с пробелами.** `new URL(...).pathname` отдаёт процентно-кодированный
путь, а `import.meta.url === \`file://${process.argv[1]}\`` даёт `false` — из-за
второго `npm start` молча завершался бы, ничего не запустив. Везде
используется `fileURLToPath`.
