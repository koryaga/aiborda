# Модели из настроек pi: спецификация

Дата: 2026-08-20. Дополняет `2026-08-19-dom-agent-design.md` §4; расхождения
разрешаются в пользу этого документа.

## Задача

Провайдер `openrouter` настроен в pi, но в селекторе dom-agent его нет. Причина
шире вопроса: `models.json` содержит только **пользовательские** провайдеры, а
встроенные в pi живут в самом пакете `pi-ai` и в `auth.json`. Наш загрузчик
читает только первый файл, поэтому невидимы все встроенные сразу.

| провайдер | моделей | видно сейчас |
|---|---|---|
| openrouter | 346 | нет |
| openai | 38 | нет |
| google | 22 | нет |
| anthropic | 13 | нет |
| openai-codex | 7 | нет |

## Проверенное перед проектированием

Факты из установленного `@earendil-works/pi-ai@0.84.2` и из реального конфига
пользователя. Не перепроверять, альтернатив не изобретать.

- `getBuiltinProviders()` даёт 39 встроенных провайдеров; `getBuiltinModels(id)`
  даёт зашитый в пакет список моделей. Списки совпадают с кэшем pi в
  `models-store.json` с точностью до единиц.
- `builtinProviders()` даёт объекты `Provider` с полями
  `id, name, baseUrl, headers, auth, getModels, refreshModels, filterModels,
  stream, streamSimple`.
- **Провайдер несёт собственный `.stream()`**, поэтому api-тип перестаёт быть
  нашей заботой: `openai-responses`, `google-generative-ai` и
  `openai-codex-responses` работают без единой строчки адаптера.
- В `models.js` ключ разрешается как `apiKey = options?.apiKey ?? auth.apiKey`,
  то есть явно переданный ключ **побеждает** разрешение через хранилище
  учётных данных. `CredentialStore` реализовывать не нужно.
- `~/.pi/agent/settings.json` содержит `enabledModels` — отобранный
  пользователем список ссылок вида `провайдер/id`, а также `defaultProvider` и
  `defaultModel`.
- Форма учётных записей в `auth.json`: `{type:'api_key', key}` либо
  `{type:'oauth', access, refresh, expires, accountId}`, где `expires` —
  число.
- Все 8 записей `enabledModels` пользователя разрешаются в настоящие модели:
  шесть на ключе, две на oauth-провайдере `openai-codex`.

## Решения

### Источник списка моделей

Авторитетный список — `enabledModels` из `settings.json`. Селектор показывает
ровно его.

Это снимает проблему четырёхсот моделей целиком: у пользователя в списке
восемь, они помещаются в обычный `<select>` без фильтров и без нового UI. И
это соответствует духу проекта — читать конфигурацию pi, а не заводить свою.

Если поля нет, оно пусто или файл отсутствует — прежнее поведение как
запасное: всё из `models.json` плюс discovery. Встроенные провайдеры в этом
режиме не добавляются: без отобранного списка они дали бы те самые четыреста
пунктов.

### Разрешение ссылки

Ссылка режется по **первому** слэшу: идентификаторы моделей сами содержат
слэши. `openrouter/nvidia/nemotron-3-ultra-550b-a55b:free` — это провайдер
`openrouter` и id `nvidia/nemotron-3-ultra-550b-a55b:free`.

Порядок поиска: сначала пользовательские провайдеры из `models.json`, затем
встроенные. **Пользовательский побеждает** при совпадении имени и id: он
настроен явно, значит нужен именно он. Это не теория — `deepseek` есть и там,
и там.

Неразрешимая запись — неизвестный провайдер, модель отсутствует у провайдера,
ключ не найден — в селектор не попадает; вместо неё уходит заметка. Заметки
уже чистятся через `scrub` перед отправкой в браузер.

### Ключи

Нынешняя цепочка сохраняется: `models.json` → `auth.json` → переменная
окружения. Добавляется чтение oauth-учётки.

**oauth только на чтение.** Берём сохранённый `access`, не обновляем его
никогда и не пишем в `~/.pi/agent/*` ни при каких условиях. Причина: обновление
обычно выдаёт новый refresh-токен и гасит старый, поэтому обновление без записи
обратно сломает вход у самого pi, а запись означала бы правку чужого конфига и
гонку за токен при одновременной работе с pi.

Истёкший токен виден локально по полю `expires`, без сетевого запроса. Такая
модель в селектор не попадает, заметка говорит войти заново через pi.

### Отправка запроса

Встроенные модели уходят через `provider.stream(model, context, {apiKey,
signal, maxTokens})`. Пользовательские остаются на нынешнем пути через
адаптеры `openai-completions` и `anthropic-messages`: он написан, покрыт
тестами и трогать его незачем.

Открытый вопрос, закрываемый первым шагом реализации: примет ли путь
`openai-codex-responses` oauth-токен, переданный как `apiKey`, или ему нужен
ещё и заголовок с `accountId`. **Если не примет — модели этого провайдера
пропускаются с заметкой**, ровно как истёкший токен. Отдельной работы по
oauth сверх этого не ведётся.

### Умолчание

`defaultProvider` и `defaultModel` предвыбираются в селекторе. Сейчас всегда
выбирается первая модель списка.

## Файлы

Новый `server/pi-settings.js` — чтение `settings.json`: отобранный список и
умолчание, одна ответственность. `pi-config.js` уже 178 строк и растёт;
третий файл конфигурации туда мешать не стоит.

Правятся: `pi-config.js` (встроенные провайдеры, oauth-ключ, разрешение
ссылок), `index.js` (выбор пути отправки), `web/shell.js` (предвыбор
умолчания).

Наружу в браузер по-прежнему уходит только `{provider, id, contextWindow}` и
заметки после `scrub`. Периметр не меняется.

## Приёмочные проверки

1. Селектор показывает ровно записи из `enabledModels`, не больше
2. Предвыбран `defaultProvider`/`defaultModel`
3. `openrouter/nvidia/nemotron-3-ultra-550b-a55b:free` разрезается верно:
   провайдер `openrouter`, id с двумя слэшами внутри
4. `deepseek` из `models.json` побеждает встроенный `deepseek`
5. Неразрешимая запись даёт заметку и не роняет загрузку
6. Истёкший oauth-токен: модель скрыта, заметка про повторный вход
7. Ни один файл в `~/.pi/` не открывается на запись
8. Ключи и `baseUrl` по-прежнему отсутствуют в трафике браузера
9. Пустой или отсутствующий `settings.json` даёт прежнее поведение
10. Ход на `openrouter/openrouter/free` доходит до ответа модели
11. Ни один тест не ходит в сеть
