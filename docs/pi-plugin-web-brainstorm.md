# Плагин pi с веб-интерфейсом — исследование и брейншторм

Дата: 2026-08-29. Исследована версия `@earendil-works/pi-coding-agent` **0.84.4**
(распакован тарбол с npm: `docs/`, `examples/`, `dist/*.d.ts`).

Задача, которую разбираем: **не отдельное приложение на Node, а полноценный
плагин к pi**, который после установки даёт работать с pi в том числе через
веб-страницу. Требование к UI: максимально похоже на pi в командной строке —
лента сообщений растёт вниз, каждое новое сообщение выталкивает предыдущие
вверх, поле ввода прижато к низу.

Это ревизия и развитие [alternative-pi-plugin.md](alternative-pi-plugin.md),
где вариант с плагином был отложен в пользу SDK. С тех пор изменилось два
факта: в 0.84 появился `expandPromptTemplates` (плагин может запускать
слэш-команды и скиллы), и в npm появился работающий прецедент — расширение,
которое делает ровно то, что здесь описывается.

---

## 1. Проверенные факты (не перепроверять)

### 1.1 Как объявляется и ставится плагин

Точка входа — функция по умолчанию, синхронная или асинхронная:

```ts
import type { ExtensionAPI } from "@earendil-works/pi-coding-agent";
export default function (pi: ExtensionAPI): void { … }
```

Расширения грузятся через [jiti], поэтому TypeScript работает без сборки —
можно публиковать `src/*.ts` и не держать шаг компиляции.

Автоподхват из доверенных мест:

| путь | область |
|---|---|
| `~/.pi/agent/extensions/*.ts` или `*/index.ts` | глобально |
| `.pi/extensions/*.ts` или `*/index.ts` | проектный (только после доверия проекту) |

Плюс через `~/.pi/agent/settings.json`:

```json
{ "packages": ["npm:pi-aiborda@0.1.0"], "extensions": ["/path/to/ext.ts"] }
```

Пакет для npm объявляется манифестом `pi` в `package.json`; для галереи на
`pi.dev/packages` нужен keyword `pi-package`:

```json
{
  "name": "pi-aiborda",
  "keywords": ["pi-package"],
  "pi": { "extensions": ["./src/index.ts"], "skills": ["./skills"] },
  "peerDependencies": { "@earendil-works/pi-coding-agent": "*", "typebox": "*" },
  "dependencies": { "ws": "^8.21.3" }
}
```

Правило по зависимостям жёсткое: `@earendil-works/pi-ai`,
`@earendil-works/pi-agent-core`, `@earendil-works/pi-coding-agent`,
`@earendil-works/pi-tui`, `typebox` — **только в `peerDependencies` с `"*"`**,
их даёт сам pi. Всё остальное — в `dependencies` (pi ставит пакет через
`npm install --omit=dev`, поэтому `devDependencies` в рантайме нет).

Если манифеста `pi` нет, работают конвенционные каталоги: `extensions/`,
`skills/`, `prompts/`, `themes/`.

### 1.2 Что даёт `ExtensionAPI` — то, на чём держится веб-режим

| метод | зачем нам |
|---|---|
| `pi.registerCommand("web", { handler })` | `/web` — поднять сервер, напечатать URL |
| `pi.sendUserMessage(text, opts)` | ход из браузера; ведёт себя как набранный человеком |
| `pi.sendMessage({customType, content, display})` | служебное сообщение в контекст |
| `pi.appendEntry(type, data)` | запись в сессию **мимо** контекста LLM |
| `pi.registerTool(def)` | наши инструменты (`page_exec`, `web_ask_*`) |
| `pi.getCommands()` | список слэш-команд для автодополнения в вебе |
| `pi.setModel`, `pi.setThinkingLevel`, `pi.getThinkingLevel` | переключатели в UI |
| `pi.getActiveTools() / setActiveTools(names)` | ленивое включение инструментов |
| `pi.registerShortcut`, `pi.registerFlag` | `Ctrl+…` открыть браузер, `--web` |
| `pi.events.on/emit` | шина между расширениями |

`sendUserMessage(content, options)` — ключевой:

- когда агент простаивает — отправляет сразу и **всегда запускает ход**;
- когда агент стримит — `deliverAs` **обязателен**, иначе бросает:
  `"steer"` (доставить после текущих тулколлов) или `"followUp"` (дождаться
  конца);
- `expandPromptTemplates: true` — **диспетчеризует слэш-команды расширений и
  разворачивает скиллы и prompt-шаблоны**. Это и есть то, чего не хватало в
  0.83 (см. §1.5).

Из `ExtensionContext` (приходит в каждый хендлер) нужны:
`ctx.sessionManager` (чтение истории), `ctx.abort()`, `ctx.isIdle()`,
`ctx.hasPendingMessages()`, `ctx.model`, `ctx.scopedModels`,
`ctx.getContextUsage()`, `ctx.compact()`, `ctx.mode`, `ctx.hasUI`,
`ctx.signal`, `ctx.cwd`, `ctx.shutdown()`.

Из `ExtensionCommandContext` (только в хендлере команды) — привилегированные
операции над сессиями: `ctx.newSession()`, `ctx.fork(entryId)`,
`ctx.switchSession(path)`, `ctx.navigateTree(id)`, `ctx.reload()`,
`ctx.waitForIdle()`.

### 1.3 События — из чего собирается лента

Порядок за один ход:

```
input → before_agent_start → agent_start
  ├ turn_start → context → before_provider_request
  │   message_start / message_update* / message_end
  │   tool_execution_start → tool_call → tool_execution_update* → tool_result → tool_execution_end
  └ turn_end
agent_end → agent_settled
```

Существенное для нас:

- `input` — **срабатывает и на ввод в TUI** (`event.source` = `"interactive"`
  | `"rpc"` | `"extension"`). Значит веб видит, что человек набрал в терминале,
  и наоборот. Двусторонность бесплатна.
- `message_update` несёт `assistantMessageEvent` — потокенный дельта-стрим.
  Это то, из чего рисуется печатающийся ответ.
- `message_start` / `message_end` — для user, assistant и toolResult.
- `tool_execution_*` — жизненный цикл вызова инструмента с `partialResult`.
- `agent_settled` — «pi точно больше ничего сам не запустит» (в отличие от
  `agent_end`, после которого возможны авторетрай и автокомпакция).
- `ui_prompt_start` / `ui_prompt_end` — pi ждёт ответа человека в диалоге
  расширения (`select`/`confirm`/`input`/`editor`/`custom`). Веб может показать
  «жду ответа в терминале» вместо «работаю».
- `session_start` (`reason`: startup | new | resume | fork), `session_shutdown`
  (`reason`: quit | reload | new | resume | fork), `session_info_changed`,
  `session_compact`, `model_select`, `thinking_level_select`.
- `queue_update` — в списке событий RPC; прецедент (§1.5) подписывается на
  него и из расширения. В `docs/extensions.md` не документирован — проверить
  экспериментом, но не закладываться.

### 1.4 Режимы запуска

| режим | `ctx.mode` | `ctx.hasUI` |
|---|---|---|
| интерактивный TUI | `"tui"` | `true` |
| `--mode rpc` | `"rpc"` | `true` |
| `--mode json` | `"json"` | `false` |
| `-p` (print) | `"print"` | `false` |

Отсюда сразу два сценария запуска одного и того же плагина:

- **`pi` в терминале + `/web`** — веб как вторая поверхность рядом с TUI;
- **`pi --mode rpc -e <плагин>`** — headless-демон, где браузер вообще
  единственный интерфейс, терминала нет. `hasUI` там `true`, диалоги работают
  через RPC-подпротокол.

### 1.5 Прецедент: `@kefka/pi-web` 0.1.7

В npm уже лежит расширение, делающее ровно эту задачу: «`/web` — локальная
веб-консоль в том же процессе pi, разделяющая сессию с TUI (поток сообщений,
исполнение инструментов, статус; отправка сообщений, переключение сессий,
fork, навигация по дереву, смена модели и уровня рассуждений)». WebSocket,
JSON-RPC 2.0, React 19 + Vite + Tailwind + shadcn, `ws` на сервере. Есть
второй бинарь `pi-web`, который делает `PI_WEB_SERVICE=1 pi --mode rpc
--extension <вход>` — то есть headless-режим из §1.4.

Это не повод не делать своё (у нас другой UI-контракт и своя фишка — холст,
§5), но **бесплатный источник уроков**. Что оттуда взято как факт:

1. **Фабрика расширения перезапускается при смене сессии** (`/new`, `/resume`,
   `/fork`) с новым объектом `api`. Модульный кэш держит только импорт, тело
   фабрики выполняется заново. Отсюда: сервер и токен — в **модульном
   синглтоне** (или на `globalThis`), а `api`/`ctx` перепривязывать при каждом
   прогоне фабрики. Иначе после `/new` вещание оборвётся, а RPC будет дёргать
   мёртвый `api`.
2. **Захваченный `ExtensionCommandContext` протухает** после замены сессии
   (ошибка содержит `"stale"`). Привилегированные операции (new/fork/switch/
   tree) надо перезахватывать: операция, начатая из веба, возвращает свежий
   ctx через колбэк и продолжает цепочку; после ручного переключения в TUI эти
   возможности деградируют до «перезапустите `/web`».
3. **Событийный `ctx` создаётся заново на каждое событие**, геттеры
   разрешаются динамически — захваченный в `session_start` живёт всю сессию.
   В зазоре между сессиями его надо обнулять.
4. `/reload` и выход роняют сервер (модуль переоценивается, старый хэндл
   теряется) — закрывать сервер в `session_shutdown` с `reason` `reload`/`quit`.
5. Безопасность: только `127.0.0.1` + случайный токен в URL, проверяемый и на
   HTTP, и на WS-хэндшейке.
6. Их README честно фиксирует ограничение 0.83: «нельзя выполнять команды
   расширений из веба — `sendUserMessage` жёстко пропускает обработку команд».
   **В 0.84 это снято** флагом `expandPromptTemplates`. Проверить в первую
   очередь — от этого зависит, будут ли в вебе рабочие `/`-команды.

### 1.6 Ассеты pi, до которых плагин дотягивается легально

Публично экспортируются из `@earendil-works/pi-coding-agent`:

- `getThemesDir()` — каталог со **штатными темами pi** (`dark.json`,
  `light.json` + `theme-schema.json`), `getCustomThemesDir()` — пользовательские;
- `getExportTemplateDir()` — каталог HTML-экспорта сессии: `template.html`,
  `template.css` (22 КБ), `template.js` (77 КБ, с `marked` и `highlight.js`),
  `ansi-to-html.js`, `tool-renderer.js`;
- `Theme`, `initTheme`, `getMarkdownTheme`, `highlightCode`,
  `getLanguageFromPath`;
- `getSessionsDir()`, `getAgentDir()`, `getSettingsPath()`, `CONFIG_DIR_NAME`,
  `VERSION`;
- `SessionManager`, `parseSessionEntries`, `buildContextEntries` — чтение
  истории из `.jsonl`;
- `RpcClient` — если понадобится вариант B (§2).

Функция `exportSessionToHtml` **не** реэкспортируется из корня, а карта
`exports` в `package.json` закрывает глубокие импорты (`.`, `./rpc-entry`,
`./client`). Но `getExportTemplateDir()` даёт путь — файлы можно прочитать и
использовать как референс стиля или отдать как статику.

Тема — это JSON вида `{"vars": {...}, "colors": {...}}`, где `colors`
ссылаются на `vars`. То есть **палитра терминального pi конвертируется в
CSS-переменные механически**, и веб получает ровно те же цвета, что TUI,
включая пользовательскую тему.

## 2. Три архитектуры и выбор

| | A. Плагин в процессе pi | B. Внешний RPC-клиент | C. Приложение на SDK (нынешняя aiborda) |
|---|---|---|---|
| Запуск | `pi` → `/web`, либо `pi --mode rpc -e …` | своя программа спавнит `pi --mode rpc` | `npm start`, свой процесс |
| Сессия | **та же, что в TUI** | своя, отдельная от TUI | своя |
| Установка | `pi install npm:pi-aiborda` | ставить и запускать вручную | `git clone && npm start` |
| Модель, ключи, скиллы, AGENTS.md | берутся из pi как есть | как есть | как есть |
| Доступ к событиям | все события расширений | подмножество, задокументированное в rpc.md | через `session.subscribe` |
| Слэш-команды, скиллы | да (`expandPromptTemplates`) | частично | нет |
| Дерево сессий, fork, resume | да | да | нет |
| Цена | жизненный цикл расширения (§6) | лишний процесс, дублирование сессии | не плагин — мимо задачи |

**Выбор — A.** Требование «полноценный плагин, который при установке даёт
работать с pi в том числе через веб» — это буквально A. B имеет смысл только
как отладочный дублёр (тот же UI можно посадить и на `RpcClient`, если
изолировать транспортный слой). C — то, что есть сейчас, и оно по определению
не удовлетворяет постановке.

Важное следствие A: **веб и терминал — две поверхности одной сессии**. Человек
набирает в TUI — веб видит; отвечает из браузера — терминал видит. Это не
бонус, а главная ценность варианта.

## 3. Устройство варианта A

### 3.1 Топология

```
процесс pi
├─ TUI (или ничего, в --mode rpc)
└─ расширение pi-aiborda
   ├─ HTTP-сервер на 127.0.0.1:<порт>   ← статика + токен
   ├─ WebSocket (ws)                    ← события вниз, команды вверх
   ├─ подписки на события pi            → лента
   └─ инструменты: page_exec, ask_*     → холст и вопросы
                     ↑
                браузер: одна страница, лента + ввод
```

Синглтон живёт в модульной области (`globalThis`-флаг переживает `/reload`),
сервер поднимается **не в фабрике**, а по `/web` или по `session_start` —
документация прямо запрещает поднимать фоновые ресурсы из фабрики: она
выполняется и в вызовах, где сессии не будет вовсе.

### 3.2 Транспорт: WS или SSE+POST

В aiborda сейчас SSE вниз + POST вверх — сознательно, чтобы не тащить `ws`
первой зависимостью помимо pi. Для плагина этот аргумент слабее: у пакета
`dependencies` всё равно свои, `ws` — 1 пакет без транзитивных.

- **WebSocket (`ws`)**: одно соединение, симметрия, естественный
  request/response с `id`, дешёвая отмена. Прецедент выбрал его.
- **SSE + POST**: ноль зависимостей, переживает прокси, автопереподключение
  в браузере из коробки. Но каждый ход из веба — отдельный POST, и нужен
  ручной коррелятор (у нас он уже написан — `server/bridge.js`).

Рекомендация: **WS**, с изоляцией транспорта за одним интерфейсом
(`send(event)` / `onCommand(cmd)`), чтобы SSE остался запасным путём.

### 3.3 Протокол

Вниз — события, один-в-один с событиями pi плюс два синтетических:

```
hello       { version, model, cwd, sessionId, theme, commands, skills }
history     { messages: [...] }                 ← гидратация при загрузке
message_start / message_update / message_end
tool_execution_start / _update / _end
turn_start / turn_end / agent_start / agent_end / agent_settled
state       { idle, queued, model, thinking, contextUsage }
ui_prompt_start / ui_prompt_end
session_start / session_info_changed / model_select / thinking_level_select
```

Вверх — команды:

```
prompt      { text, images?, deliverAs? }   → pi.sendUserMessage
abort                                        → ctx.abort()
compact                                      → ctx.compact()
setModel / setThinkingLevel
newSession / switchSession / fork / navigateTree
listSessions / getTree / getMessages
answer      { askId, value }                 → ответ на web_ask_*
```

Главное правило: **веб не хранит истину**. Истина — сессия pi; веб
восстанавливает её из `history` при каждом подключении и потом только
догоняет событиями. Это ровно противоположно нынешнему инварианту aiborda
(«снимок не отправляется никогда, только диф»), и здесь это правильно: чат
без снимка не восстановишь после F5.

### 3.4 Гидратация истории

`ctx.sessionManager.getEntries()` → фильтр `type === "message"` → склейка
`toolResult` по `toolCallId` с вызовами из assistant-сообщения → массив
`{role, text, thinking, toolCalls[]}`. Пустые сообщения отбрасывать. Ровно
этот алгоритм реализован в прецеденте (`session-history.ts`), типы записей
описаны в `docs/session-format.md`.

Для «открыть чужую/прошлую сессию» в вебе — `SessionManager` умеет читать
произвольный `.jsonl` из `getSessionsDir()`.

## 4. UI: «как pi в терминале»

### 4.1 Что означает требование

Лента растёт **вниз**: новое сообщение появляется внизу и выталкивает
предыдущие вверх; поле ввода прижато к нижнему краю; ничего не
перерисовывается задним числом, кроме текущего стримящегося блока. Это
поведение терминала, и оно же — поведение обычного чата. Инверсия («новое
сверху») — не то, что делает pi, и делать её не надо.

Три уровня верности, выбирать осознанно:

| уровень | что это | цена |
|---|---|---|
| 0. Терминальная эстетика | моноширинный шрифт, палитра из темы pi, лента без «пузырей», префиксы `>` / `⏺` | день |
| 1. Верность разметке | markdown и подсветка кода как у pi (`marked` + `highlight.js` из `getExportTemplateDir()`), диффы, свёрнутые тулколлы | неделя |
| 2. Верность рендеру | прогон настоящих TUI-компонентов и `ansi-to-html` | высокая, ломкая |

Целимся в **1**. Уровень 2 — тупик: `ToolExecutionComponent` и прочие требуют
живого терминала, а `ansi-to-html` даёт HTML, который не переживает
resize браузера.

### 4.2 Палитра — механически из темы pi

`getThemesDir()` → `dark.json` / `light.json`; активная тема пользователя —
через `ctx.ui.getTheme()` в TUI-режиме (в RPC вернёт `undefined`, тогда падать
на `dark`). Разворачиваем `vars` → `colors` и печатаем в CSS:

```css
:root {
  --pi-text: #d4d4d4;      --pi-accent: #8abeb7;
  --pi-muted: #808080;     --pi-dim: #666666;
  --pi-user-bg: #343541;   --pi-tool-ok-bg: #283228;
  --pi-tool-err-bg: #3c2828; --pi-tool-pending-bg: #282832;
  --pi-md-heading: #f0c674; --pi-md-link: #81a2be; --pi-md-code: var(--pi-accent);
}
```

Тогда смена темы в pi меняет и веб — одним источником правды. Заодно решается
светлая/тёмная тема: она не «наша», а пользовательская.

### 4.3 Анатомия ленты

- **сообщение человека** — фон `userMessageBg`, без пузыря, во всю ширину
  колонки; префикс `>` как в TUI;
- **ответ модели** — markdown, ширина колонки ~100 символов (`ch`), чтобы
  переносы совпадали с терминальными;
- **рассуждения** — цветом `thinkingText`, свёрнуто по умолчанию, во время
  стрима заголовок «Thinking…», после — «Thought»; разворачивается на месте,
  не в модалке;
- **вызов инструмента** — одна строка `⏺ bash  ls -la` с фоном
  `toolPendingBg` → `toolSuccessBg`/`toolErrorBg` по завершении; клик
  разворачивает аргументы и вывод; `tool_execution_update` дописывает вывод
  в живом виде (это и лечит «оболочка молчит десятки секунд» из TODO);
- **футер** — модель, уровень рассуждений, занятость контекста, стоимость,
  индикатор занятости; ровно те поля, что в футере TUI;
- **очередь** — когда агент занят, а человек жмёт Enter: показывать «в
  очереди ×N» и слать с `deliverAs: "followUp"`.

### 4.4 Поведение ввода и скролла

- `Enter` отправляет, `Shift+Enter` — перенос строки. (В нынешней aiborda
  `Ctrl+Enter`, потому что поле однострочное; для чата привычнее Enter.)
- Кнопка справа от поля: **↑ отправить** когда простой, **■ остановить**
  когда идёт ход. Одна кнопка, два состояния — как `Esc` в TUI.
- Автоскролл «липкий»: доскроллено до низа — держим низ; человек прокрутил
  вверх — не дёргаем, показываем «↓ новые сообщения».
- `/` в начале строки — выпадашка команд из `pi.getCommands()` и скиллов;
  `@` — файлы из `ctx.cwd`.
- История ввода стрелками вверх/вниз, как в TUI.

## 5. Что делать с нынешней aiborda

Нынешняя aiborda — не чат, а **холст**: модель отвечает не текстом, а
перестройкой DOM через `page_exec`; человек правит страницу руками, и правки
приходят дифом. Требование этой задачи — чат как в CLI. Это два разных
продукта, и подменять один другим жалко: холст — единственное, чем aiborda
отличается от `@kefka/pi-web`.

**Предложение: один плагин, две поверхности.**

```
http://127.0.0.1:<порт>/?token=…
├─ вкладка «Чат»   — лента как в CLI (основной режим, §4)
└─ вкладка «Холст» — нынешний образ + page_exec (уникальная фича)
```

Что это даёт:

- **решается TODO про потерянный финальный текст.** Сегодня закрывающая
  реплика модели уходит в stdout мимо страницы, потому что оболочка физически
  не умеет её показать. В плагине лента — штатный приёмник текста; холст
  перестаёт быть единственным каналом, и противоестественное требование
  «никогда не отвечай текстом» из `AGENTS.md` можно смягчить до «показывай
  результат на холсте, объясняй в чате»;
- **page_exec становится обычным инструментом среди прочих** — его вызовы
  видны в ленте карточкой, как `bash`, а не только в терминале;
- изоляция сохраняется тем же механизмом: холст — на **отдельном порту** (свой
  origin), чат — на основном. Инвариант «код модели бессилен снаружи образа»
  держится Same-Origin Policy, а не `sandbox`, ровно как сейчас;
- диф-канал (`image-boot.js`, самая тонкая и уже оттестированная часть
  проекта) переносится без изменений; правки человека на холсте уходят в
  `sendUserMessage` вместо прямого `session.prompt`.

Что переиспользуется как есть:

| файл | судьба |
|---|---|
| `web/image-boot.js` | переносится дословно (холст) |
| `web/image.html`, `style.css` | переносятся |
| `server/bridge.js` | переносится, если останется SSE; при WS упрощается |
| `server/agent.js` | `createPageTool` остаётся, `startSession` уходит |
| `server/index.js` | переписывается: статику и роуты забирает сервер плагина |
| `server/stream-log.js` | не нужен — поток идёт в ленту, а не в stdout |
| `test/image-*.test.js` | переносятся; это 2/3 тестов и они самые ценные |
| `AGENTS.md` | переписывается: контракт «только DOM» → «чат + холст» |

## 6. Подводные камни

Собрано из документации, прецедента и собственного опыта проекта.

1. **Фабрика перезапускается на каждой смене сессии.** Синглтон — в модуле или
   на `globalThis`; в фабрике только перепривязка `api`. Разрешение
   пользователя (если введём) хранить отдельно от флага загрузки, иначе
   `/reload` его сбросит.
2. **Не запускать сервер из фабрики** — документация прямо запрещает: фабрика
   выполняется и там, где сессии не будет. Только `session_start` или `/web`.
3. **`session_shutdown` идемпотентен** и приходит с разными `reason`. На
   `quit`/`reload` — закрывать сервер; на `new`/`resume`/`fork` — **не
   закрывать**, иначе веб отваливается при каждом `/new`.
4. **`ExtensionCommandContext` протухает** после замены сессии. Ошибка со
   словом `stale` — сигнал перезахватить, а не паниковать.
5. **`sendUserMessage` во время стрима без `deliverAs` бросает.** Всегда
   спрашивать `ctx.isIdle()` и выбирать `steer`/`followUp` осознанно. Наш
   выбор для чата — `followUp` (steer подрезает текущий ход и путает ленту).
6. **`message_update` — поток дельт, а не снимок.** Копить на клиенте; на
   `message_end` заменять накопленное финальным сообщением (оно может
   отличаться: `message_end` разрешено переписывать другим расширениям).
7. **Порядок в параллельном режиме инструментов**: `tool_execution_end`
   приходит в порядке завершения, а `toolResult`-сообщения — в порядке
   вызовов. Лента должна класть карточку по `toolCallId`, а не по времени.
8. **Диалоги других расширений** (`ctx.ui.confirm` из чужого плагина) рисуются
   в TUI, а веб их не видит — только `ui_prompt_start`. Показывать в вебе
   баннер «pi ждёт ответа в терминале», не пытаться перехватить.
9. **`ctx.mode === "rpc"`**: `custom()` возвращает `undefined`, `getTheme()` —
   `undefined`, `setTheme()` — ошибку. Всё, что читает тему, должно иметь
   запасной путь на файл из `getThemesDir()`.
10. **Порт занят.** Прецедент: `/web --port 0` (случайный) по умолчанию,
    повторный `/web` только печатает URL, не перезапускает.

## 7. Безопасность

Периметр тот же, что у нынешней aiborda, плюс один новый пункт.

- Слушать **только `127.0.0.1`**, никогда `0.0.0.0`.
- **Случайный токен** в URL, проверяемый и на HTTP-запросах, и на
  WS-хэндшейке. Петля — не граница: у любого локального процесса есть доступ
  к порту.
- **Проверка `Host`** на каждом запросе (`127.0.0.1:<порт>` или
  `localhost:<порт>`) — защита от DNS rebinding. Урок уже усвоен в
  `server/index.js`, перенести дословно: CORS запрещает читать чужой ответ, а
  не слать запрос, поэтому отсутствие CORS-заголовков само по себе не защита.
- **Проверка `Origin`** на WS-хэндшейке — у WebSocket нет Same-Origin Policy
  вообще, это новый по сравнению с SSE пункт.
- Веб-страница даёт полный доступ к агенту, у которого нет гейтов на `bash` и
  `write`. Значит открытый порт = удалённое выполнение кода. Токен — не
  украшение.
- Prompt injection остаётся значимым риском: модель ходит в интернет, а её
  вывод рисуется как HTML в ленте. **Markdown рендерить с санитайзером**,
  никакого `innerHTML` из текста модели. На холсте — наоборот, произвольный
  код разрешён по построению, и именно поэтому холст живёт на отдельном
  origin.

## 8. Вехи

**M0. Скелет плагина (полдня).** `package.json` с `pi.extensions`,
`src/index.ts`, `/web` поднимает HTTP на случайном порту и отдаёт «hello».
Проверка: `pi -e ./src/index.ts`, затем `pi install` из локального пути.
Ответ на вопрос «вообще заводится ли».

**M1. Лента только на чтение (2–3 дня).** WS, подписка на события, гидратация
из `sessionManager`, стриминг ответа, карточки инструментов. Человек печатает
в TUI — видит в браузере. Уровень верности 0.

**M2. Двусторонний ход (2–3 дня).** Поле ввода → `sendUserMessage`,
очередь/`followUp`, кнопка «стоп» → `ctx.abort()`, футер со статусом и
моделью. Здесь же проверить `expandPromptTemplates` и решить судьбу
слэш-команд в вебе.

**M3. Верность разметке (3–4 дня).** Тема pi → CSS-переменные, markdown +
подсветка, диффы для `edit`, свёртки, «липкий» скролл, автодополнение `/` и
`@`. Уровень 1.

**M4. Холст (2–3 дня).** Вторая вкладка на отдельном порту, перенос
`image-boot.js` и `page_exec`, правки человека → `sendUserMessage`. Переписать
`AGENTS.md` под две поверхности.

Дальше по вкусу: список и дерево сессий, `resume`/`fork` из браузера,
`web_ask_*` (блокирующие вопросы к человеку из инструмента),
`--mode rpc`-демон, публикация в npm с keyword `pi-package`.

## 9. Открытые вопросы — проверить экспериментом, не рассуждением

1. **Работает ли `expandPromptTemplates: true` для команд расширений?**
   От ответа зависит, будут ли в вебе живые `/`-команды или только текст.
   Прецедент фиксирует, что в 0.83 не работало.
2. **Приходит ли `queue_update` в расширения?** В `docs/extensions.md` его нет,
   в `docs/rpc.md` есть, прецедент подписывается. Если нет — очередь считать
   самим по `isIdle()`/`hasPendingMessages()`.
3. **Что именно возвращает `ctx.ui.getTheme()` в TUI** — объект `Theme` или
   имя. От этого зависит путь «тема pi → CSS».
4. **Переживает ли `globalThis`-синглтон `/reload`** в 0.84 (прецедент
   утверждает, что модуль переоценивается и хэндл сервера теряется — надо
   понять, какой именно из двух механизмов действует).
5. **Как ведёт себя `sendUserMessage` из веба, когда фокус в TUI** — не
   ломается ли редактор терминала. Это главный риск «двух поверхностей».
6. **Насколько дорого гидратировать длинную сессию** (сотни записей) —
   нужна ли пагинация `history` с самого начала.

## 10. Итог одним абзацем

Плагин делается вариантом A: расширение в процессе pi, синглтон-сервер на
`127.0.0.1` с токеном, WS вниз-вверх, лента собирается из штатных событий
`message_*` / `tool_execution_*` и гидратируется из `sessionManager`, ход из
браузера идёт через `sendUserMessage` с `deliverAs`. Верность CLI берётся не
эмуляцией терминала, а тремя дешёвыми вещами: палитрой из настоящей темы pi,
моноширинной колонкой фиксированной ширины и лентой, растущей вниз с прижатым
низом. Уникальность aiborda — холст с `page_exec` — сохраняется второй
вкладкой на отдельном origin, и заодно закрывает старую проблему с
потерянным финальным текстом модели. Прецедент `@kefka/pi-web` показывает,
что схема рабочая, и даёт готовый список граблей жизненного цикла.
